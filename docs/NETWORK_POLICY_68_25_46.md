# 10.10.206.25 / 10.10.206.68 / 10.10.207.46 网络策略差异报告

> 采集时间：2026-11-06 12:00–12:15（Asia/Shanghai）
> 生产盒子 `10.10.207.46` 只读采集，未修改任何文件/配置。

## 结论

三台盒子在**同一 /23 网段、同一默认网关**，本机都没有拦截 ISC 的 iptables/nft 规则，
`rp_filter` 都是 `2`。但实测：

- `10.10.206.25` 到 `10.10.69.250` 的 **443/554/1935/83 全部 OPEN**；
- `10.10.206.68` 到同样四个端口 **全部 CLOSED**；
- `10.10.207.46` 当前有 **25 条**到 `10.10.69.250:1935` 的 RTMP 连接。

因此不是“路由不通”，也不是 `.68` 本机防火墙；差异在 **ISC 侧/中间安全设备针对源 IP
（或源 MAC）的 ACL、NAT、会话策略**。网关人员如果说“两边策略一样”，需要他们拿出
`.25` 与 `.68` 的源 IP 放行记录/ACL 命中计数做对照，而不是只看路由。

## 实测对比

|---|---|---|---|
| 地址 | `10.10.206.25/23`，DHCP | `10.10.206.68/23`，static | `10.10.207.46/23`，static |
| 默认网关 | `10.10.207.254` | `10.10.207.254` | `10.10.207.254` |
| 同网段路由 | `10.10.206.0/23 dev eth0` | `10.10.206.0/23 dev eth0` | `10.10.206.0/23 dev eth0` |
| `rp_filter` | 2 | 2 | 2 |
| 本机 iptables | 仅 Docker 规则 | 仅 Docker 规则 | 仅 Docker 规则 |
| 到 ISC 443 | OPEN | **CLOSED** | 生产在用 |
| 到 ISC 554 | OPEN | **CLOSED** | 生产在用 |
| 到 ISC 1935 | OPEN | **CLOSED** | 生产在用 |
| 到 ISC 83 | OPEN | **CLOSED** | 生产在用 |
| ISC 并发连接 | 代理进程按需 | 经 `.25` 代理 | **25 条 1935** |

`CLOSED` 是 `timeout 2 bash -c "</dev/tcp/..."` 的结果，不是域名/DNS 问题：
三台机器都用 IP 直连，路由表都经 `10.10.207.254`。

## 为什么说不是本机防火墙

`.68` 上：

```text
iptables -S        # 只有 Docker 的 FORWARD/ NAT 规则
nft list ruleset   # 无拦截 ISC 的规则
cat /proc/sys/net/ipv4/conf/all/rp_filter   # 2
ip route           # default via 10.10.207.254 dev eth0
```

如果是 `.68` 本机拦截，`iptables`/`nft` 会有对应 DROP/REJECT 计数；实际没有。
之前的抓包也显示对端先回 RST、随后又回 SYN-ACK，属于中间设备/对端策略异常，
而不是本机协议栈拒绝。

## 需要网关/安全运维核查的点

1. **源 IP ACL**：ISC `10.10.69.250` 或其前置防火墙/负载均衡上，是否存在只允许
   `10.10.206.25`、不允许 `10.10.206.68` 的源地址白名单。
2. **源 MAC/ARP 绑定**：`.25` 是 DHCP，`.68` 是静态；若 ISC 侧按 MAC 注册，
   需要登记 `.68` 的 MAC（`e0:a5:09:22:31:a1`）。
3. **NAT/代理策略**：中间设备是否把 `.25` 的流量做了 SNAT 到另一个受信源地址，
   而 `.68` 没有；请给出两者的 NAT 前后源 IP 会话表。
4. **安全组/会话表**：对比同一时间 `.25` 与 `.68` 到 `10.10.69.250:443/554/1935`
   的 ACL 命中计数；如果 `.68` 命中 deny，直接给出规则编号。
5. **生产 `.46` 的 25 条 1935 连接**：说明 ISC 对 `10.10.207.46` 是放行的；
   把 `.46` 也加入对照，能证明不是“只有 `.25` 这个网段/交换机口”的问题。

## 当前规避

开发盒 `.68` 仍通过 `.25` 的 TCP 转发访问 ISC：

- `10443 -> 10.10.69.250:443`
- `10444 -> 10.10.69.250:554`
- `10445 -> 10.10.69.250:1935`

该方案只用于开发验证；生产应让网关按 `.25`/`.46` 的放行策略给 `.68` 放行，
或把代理做成受控服务，避免 `.25` 成为单点。

补充实测（2026-11-06 12:31）：把 `.68` 强制切到 RTMP（`protocol=rtmp`，
经 `.25:10445 -> 10.10.69.250:1935`）测试凤凰咀博物馆通道，仍然
`gateway no video stream: rtmp://10.10.206.25:10445/live/openUrl/...`；说明不是
“RTSP 代理单点”问题，ISC 对 `.68` 经代理的会话同样受限/拒绝。

- `.46`：`ip -4 addr`、`ip route`、`ss -tn | grep 10.10.69.250:1935`，25 条连接
