# 10.10.206.25 与 10.10.206.68 的 ISC 网络对比报告

## 结论

**是要找网络运维/安全运维，不是先改 AI 服务代码。**

两机同网段、同网关、同 `rp_filter`、都没有本机 iptables 拦截；`.25` 到 `10.10.69.250:443` 建连成功，`.68` 被对方返回 RST（随后又收到 SYN-ACK，客户端发 RST）。这属于 **ISC 侧/中间安全设备对源 IP/MAC 的访问控制或会话策略差异**，需要网络/安全运维按 `.25` 的放行策略给 `.68` 放行。

## 实测对比

| 项目 | 10.10.206.25（可访问 ISC） | 10.10.206.68（不可访问） |
|---|---|---|
| 地址 | `10.10.206.25/23`，DHCP | `10.10.206.68/23`，static |
| MAC | `02:04:4f:88:c6:a6` | `e0:a5:09:22:31:a1` |
| 默认网关 | `10.10.207.254` | `10.10.207.254` |
| 到 ISC 路由 | via `10.10.207.254` | via `10.10.207.254` |
| `ping 10.10.69.250` | ICMP 100% 丢包 | ICMP 100% 丢包 |
| TCP 443 | `TCP_OPEN` | `Connection refused` |
| HTTPS | `301`（连接成功） | curl connect failed |
| 本机 iptables | 仅 Docker 规则，无拦截 | 仅 Docker 规则，无拦截 |
| rp_filter | `2` | `2` |
| DNS | `nameserver 127.0.0.53`，`search ccgdc.com` | `nameserver 127.0.0.53`，无 search |

## 关键抓包（10.10.206.68）

```text
10.10.206.68.52538 > 10.10.69.250.443: Flags [S]
10.10.69.250.443 > 10.10.206.68.52538: Flags [R.]
10.10.69.250.443 > 10.10.206.68.52538: Flags [S.]
10.10.206.68.52538 > 10.10.69.250.443: Flags [R]
```

含义：

- 源发出 SYN；
- 对端/中间设备先回 RST；
- 随后对端又回 SYN-ACK；
- 客户端按协议栈状态回 RST，应用层显示 `Connection refused`。

这说明不是“没有路由”或“本机防火墙”，而是**对端/中间安全策略的异常 RST + 放行策略差异**。`.25` 没有该现象。

## 需要网络/安全运维做什么

1. 在 ISC `10.10.69.250` 或其前置防火墙/负载均衡上，比较 `10.10.206.25` 与 `10.10.206.68` 的 ACL/安全组/会话策略。
2. 给 `.68` 放行到 `10.10.69.250:443` 和 `10.10.69.250:554`。
3. 如果 ISC 侧按 MAC/IP 白名单，需要登记 `.68` 的 MAC `e0:a5:09:22:31:a1` 和 IP `10.10.206.68`；`.25` 是 DHCP，`.68` 是静态，二者注册状态可能不同。
4. 可把抓包文件和上面的对比表直接发给网络运维；请求对方检查“为什么同一网段 .25 通、.68 被 RST”。

## 当前工作区规避

已在 `.25` 上启动 TCP 转发（仅内网）：

- `10443 -> 10.10.69.250:443`
- `10444 -> 10.10.69.250:554`

开发盒 AI 服务通过 `AIDETECT_ISC_PROXY` / `AIDETECT_ISC_RTSP_PROXY` 使用。该方案只用于验证，生产应让网络放行或把代理做成受控服务。
