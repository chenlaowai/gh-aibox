# 生产告警逻辑逆向：蓝框→计数→红框

> 依据：生产 `libEdgeSystem.so` 的 `AlarmEngine`/`Show` 行为、生产任务字段
> `detect_section/detect_threshold/cooldown_time`、生产告警视频观察。
> 生产盒子只读，未修改。

## 1. 生产观感

生产实时预览里，目标刚出现时是**蓝色框**（可疑，不告警）；连续命中达到配置帧数/
秒数后，框变**红色**，上沿出现告警标签，同时产生告警事件/告警图。不是“一检测到
就红框”。

这与生产任务字段一致：

- `detect_section`：滑动窗口长度；
- `detect_threshold`：窗口内需要命中的帧数；
- `cooldown_time`：告警冷却；
- `exceed_num`：目标数量阈值。

生产 `AlarmEngine` 维护每个算法的滑动窗口；窗口内 `detected` 计数达到
`detect_threshold` 且冷却通过，才生成 `AlarmJob`。UI 的蓝色框对应“窗口未满”，
红色框对应“已确认”。

## 2. 我们的旧实现问题

旧 `update_alarm` 在命中后立即 `save_alarm`，且预览把所有 `target` 框直接画红；
没有“可疑→确认”状态，所以：

- 人刚出现就红框+标签，看起来“一有框就告警”；
- 旧 `safetyhelmet` Damo 模型同时输出“戴/未戴”两类，绿色“戴安全帽”和红色
  “未戴安全帽”会叠在同一人身上（图1/图2）；
- 预览检测每 200ms 一次，10fps 预览下框最多落后 200ms，快速走动时框追不上人
  （图4/图5）。

## 3. 新实现

### 3.1 蓝框→红框

`Detection` 增加 `pending`：

- `target=true && pending=true`：蓝色框，不画标签；
- `target=true && pending=false`：红色框 + 告警标签；
- 非目标：绿色框。

`ModelRuntime` 维护**每个目标独立**的状态向量：

```text
TargetState:
  confirmed      该目标是否已经过蓝框倒计时
  first_seen_ms  该目标首次达到数量阈值的时刻
  last_seen_ms   该目标最近一次出现时刻
  rect           该目标最近框（IoU/中心距匹配）
```

`update_alarm()` 先用 IoU（>0.15）或中心距匹配当前检测到已有目标；新目标追加
新 `TargetState`，已有目标沿用；每个目标独立走：

```text
目标达到 exceed_num:
  confirmed=false: 该目标首次记录 first_seen；持续 3s -> confirmed=true
  confirmed=true : 该目标保持红色；上报仍按全局上报间隔分钟数
目标消失:
  该目标连续 1s 未匹配 -> 删除该 TargetState，下次重新蓝框计时；其它目标不受影响
```

`save_alarm` 只在某个目标确认时/上报间隔到达时调用；实时预览：

- 每个 Detection 的 `pending/confirmed/countdown_s` 由它匹配到的 `TargetState` 决定；
- `target && pending`：蓝框，框上沿显示该目标的 `3s/2s/1s`；
- `target && confirmed`：红框 + 标签，该目标不消失就一直红；
- 非目标：绿框。

这修复了“画面已有 1 个红框时，第 2 个新目标直接红框”的问题：新目标没有自己的
`TargetState`，必须重新走 3s 倒计时。

这样修复了“红框只出现一帧又变蓝”的问题：红色由 `confirmed` 状态保持，不再由
单帧 `fired` 决定。蓝框阶段在单通道预览走 OpenCV 渲染，框上沿叠加剩余秒数
`3s/2s/1s`；确认后走原来的 bmcv 中文标签路径。

### 3.2 标签不重叠

- 新 `helmet`/`vest` 分类器**只输出违规目标**（未戴安全帽/未穿反光衣），不再输出
  “戴安全帽”绿色框，因此不会出现红绿矛盾标签；
- 旧算法保留为 `*_our`（如 `安全帽检测_our`），它们仍按旧模型画“戴/未戴”两类；
  前端算法配置里可明确区分，避免和新的 `安全帽检测` 同时选；
- 新增 `dedup_dets()`：同一 class/label 内按 IoU>0.5 去重，避免同一目标多框/多标签；
- 当前 30 个任务已迁移到新算法，旧 `_our` 只作为回退选项。

### 3.3 帧率/框跟随

- 预览 10fps；
- 检测从每 200ms 提到每 **100ms**，框最多落后约 100ms；
- 检测在独立 infer 线程，预览用最新 `dets_`；不再让检测阻塞解码；
- 新增速度外推：每帧检测与上一帧按 IoU 匹配，记录 `vx/vy`（px/s）；预览时按
  `now - dets_ms_` 把框外推到当前时刻，最多 800ms，超过则丢弃；
- 这样红框会沿目标运动方向移动，不会长时间停在空地；告警保存/包环期间曾尝试外推 5s，但实测框会外推到人已离开的位置，已回退为
  800ms；保存期间宁可短暂无框，也不画错位框；
- 代价是快速转向/遮挡时会有短暂偏差，彻底贴合仍需完整 tracker/异步保存。

## 4. 与生产还差什么

1. 生产蓝框可能带“可疑”计数/倒计时，我们目前只有颜色区分，没有显示计数；
2. 生产可能有目标跟踪（同一人跨帧保持 ID），我们目前逐帧检测，快速移动会换框；
3. 生产告警图可能包含“触发前 N 秒”的轨迹，我们只画当前帧；
4. 生产 `AlarmEngine` 的确切窗口/冷却单位（帧 vs 秒）需继续用 `libEdgeSystem.so`
   反汇编确认；当前按任务字段和观察实现。

## 5. 本轮视觉验证

- 用 NoVest 视频、`detectThreshold=6` 实测到**蓝框阶段**（3.8s，尚未触发）：
  `docs/assets/alg_blue_pending.jpg`。
- 7.9s 看到**红框停在旧位置、人已经走开**：`docs/assets/alg_stale_red.jpg`，
  确认了用户图4/图5的“框不跟人”根因是预览用了过期检测结果。
- 已加 `dets_ms_`：预览检测结果超过 300ms 就丢弃，不再画旧位置红框；代价是
  推理慢时框会短暂消失，下一步需要 tracker/异步告警保存。

## 6. 验证建议

- 用生产 `NoHelmet`/`NoVest` 视频，设置 `detect_threshold=3`，观察预览前几帧蓝框、
  确认后红框；
- 用 6488 实时预览观察新 `helmet`/`vest` 是否只出现红色违规标签；
- 对比迁移前后同一摄像头的告警图，确认不再出现红绿标签叠在同一人。
