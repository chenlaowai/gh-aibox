## 2. 逻辑对比（链路 + 算法）

| 环节 | 我方实现 | 生产实现 | 是否一致 |
|---|---|---|---|
| 取流 | `IngestBridge`（libavformat 进程内拉流 → mpegts → 本地 UDP 22000+） | `StreamFactory` + `media_sdk`（进程内，无外部进程） | 形态一致，实现库不同 |
| ISC 接入 | `isc://` → 直连 RTSP/RTMP（单次 URL，失败轮换候选） | 同（ISC 客户端，streamType 0/1） | 一致 |
| 解封装 | 进程内 libavformat + mpegts 转封装 | media_sdk 内解封装 | 一致（都在进程内） |
| 解码 | **VPU 硬解** `h264_bm`/`hevc_bm`（帧在设备内存，`data[4]/[5]` 设备地址） | VPU 硬解（`DecodeInstance`，常驻不重建） | **已对齐**（路线 B 前是软件解码） |
| 帧缓冲 | 每任务复用 `BMImage`；设备侧 attach，无每帧 mmap | 每通道池化帧（常年 dmabuf 恒 133） | 已接近（见 §4） |
| 推理 | `bmrt_load_bmodel` + `bmrt_launch_tensor_ex`，输入零拷贝、输出张量复用 | `board::base_model`（bmodel） | 一致 |
| 调度 | FIFO 门票闸门 + 有界并发（默认 4）+ 多实例（同算法 ≤2） | 每任务异步 workLoop + 回调，赶不上就跳过该算法 | 语义一致 |
| 后处理 | YOLOv5/v11/Damo 自研 + 逐类 NMS + ROI + 跟踪 | 生产插件（同名算法） | 参数对齐见 §3 |
| 单通道预览 | 设备侧缩放 + 设备侧画框 + **设备侧 JPEG**（NV12→`bmcv_image_jpeg_enc`，CPU 仅回退） | `JpegEncoderInstance` 设备侧编码 | **已对齐**（`hw_jpeg_ok>0/fail=0`；质量 `AIDETECT_JPEG_QUALITY`） |
| 合流墙 | 4 组 × 3×3，设备侧画布 + `image_copy_to` + 设备侧 JPEG | `MergeInstance`（硬件合流） | 形态一致 |
| 告警图片 | 设备侧画框 + **设备侧 JPEG**（1280×720 / 原尺寸） | 设备侧编码 | **已对齐** |
| 告警视频 | `TsSegmentRecorder`：TS 2s×12 分段环 → ffmpeg remux MP4，HEVC 源转 H.264 | `dump4`：每通道常驻，取 pre/post 进程内写 MP4 | 目标一致（10s、20MB 上限），实现不同 |
| 上报 | HTTP JSON + JWT，告警图/视频路径回填 | 同（`report_address`） | 一致 |
| 配置同步 | 每 2s 从后端 reconcile（任务/ROI/算法参数热更新） | 生产由 Web 下发到 `TaskInstance` | 一致 |
| 子码流切换 | 显式 `AIDETECT_AUTO_SUBSTREAM=1` 才启用，默认按 URL `streamType` | 生产按通道配置 `streamType` | **已对齐**（默认配置驱动） |

## 6. 结论与差距

1. **逻辑栈已对齐**：取流/解码/推理/预览/合流/告警/上报的形态与生产一致；解码从软件换到 VPU 后，
   CPU 从 266~294% 降到 191~197%，dmabuf 从 500~660 降到 290 且恒定。
2. **单路 CPU 仍高于生产**（5.3% vs 3.3%）：主要差在
   ①预览/告警 JPEG 仍走 `bm_image_to_mat`+`cv::imencode`（CPU 编码，生产是设备侧）；
   ②每帧全尺寸 BGR_PLANAR 转换（生产按需缩放）。
   优化这两项预计可再降 1~2 个核。
3. **稳定性仍是短板**：生产连续 5 天 16 小时、1021 线程、dmabuf 0；我们本轮在修
   解码器生命周期崩溃（已改 `shared_ptr` + 读取前快照），需连续 24h 观察。
4. **线程模型**：生产 1021 线程（每通道多线程），我们 268~278，扩展性好但重连风暴时压力集中在少数线程。
5. **缺失的可观测项**：TPU/VPU 利用率（我方 `/get_occupancy` 返回 0）、端到端时延、告警召回/误报率。

## 8. fd / dma-buf 差异归因（2026-11-19，迭代 105）

**结论：fd、CPU、dma-buf 对象都随“有画面路数”线性增长；按每路归一化我方更低。
dma-buf 映射/对象无法在不替换解码器栈的前提下归零。**

| 归属 | 我方（34 路有画面） | 生产（10 路有画面） | 说明 |
|---|---|---|---|
| 自有 BMImage 设备内存 | 连续堆分配（默认）产生 dma-buf fd；`AIDETECT_ATTACH_MEM=1` 的 `bm_malloc_device_byte + attach` 可把 dmabuf fd 644→450、对象 2155→1237，但 VPP 写 attached 内存会让预览/合流出现彩色噪声，**默认关闭** | media_sdk 内部池化 | 视觉正确性优先，已回退默认路径 |
| 库内部（bmrt 模型/张量 + ffmpeg 解码器） | **约 615 个 dma-buf fd / 290 个进程映射** | media_sdk/board_sdk 不导出 dma-buf（0/0） | `bmrt_load_bmodel` 与 `h264_bm/hevc_bm` 内部用 dma-buf 堆；`dectest` 单解码器进程 0 映射，量级来自多模型实例 + 34 个解码上下文 |
| 内核 dma-buf 对象（bufinfo） | 1407（41.4/路） | 593（59.3/路） | 生产每路反而更多（其 media_sdk 对象更大/更多），按路我方更省 |
| 进程 fd | 713（21.0/路；dmabuf 450 + socket 121 + font 36 + 设备 ~55 + 文件/其他） | 417（41.7/路） | 每路我方更低；绝对高是 34 vs 10 路 |

**能否完全对齐**：
- **dma-buf 映射/ fd 归零**：不能，除非把解码从 `sophon-ffmpeg (h264_bm/hevc_bm)` 换成生产的
  `media_sdk DecodeInstance`（闭源、未随 release 提供）。这属于解码器选型差异，不是重连逻辑问题。
- **fd 绝对数一致**：需要把有画面路数从 34 降到约 10（与生产一致），这与“36 路都要有画面”的目标冲突；
  按每路对比我们已经更省。
- **可继续压缩的 fd**：每任务一个字体 fd（36 个）可改为进程级共享；socket 121 个约为 34 路 × 3~4，
  与双 UDP 端口（解码/告警环）一一对应，属必要开销。
