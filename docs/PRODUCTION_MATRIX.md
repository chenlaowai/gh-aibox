## 2. 逻辑对比（链路 + 算法）

| 环节 | 我方实现 | 生产实现 | 是否一致 |
|---|---|---|---|
| 取流 | `IngestBridge`（libavformat 进程内拉流 → mpegts → 本地 UDP 22000+） | `StreamFactory` + `media_sdk`（进程内，无外部进程） | 形态一致，实现库不同 |
| ISC 接入 | `isc://` → 直连 RTSP/RTMP（单次 URL，失败轮换候选） | 同（ISC 客户端，streamType 0/1） | 一致 |
| 解封装 | 进程内 libavformat + mpegts 转封装 | media_sdk 内解封装 | 一致（都在进程内） |
| 解码 | **VPU 硬解** `h264_bm`/`hevc_bm`（帧在设备内存，`data[4]/[5]` 设备地址） | VPU 硬解（`DecodeInstance`，常驻不重建） | **已对齐**（路线 B 前是软件解码） |
| 帧缓冲 | 每任务复用 `BMImage`；设备侧 attach，无每帧 mmap | 每通道池化帧（常年 dmabuf 恒 133） | 已接近（见 §4） |
| 推理 | `bmrt_load_bmodel` + `bmrt_launch_tensor_ex`，输入零拷贝、输出张量复用 | `board::base_model`（bmodel） | 一致 |
| 调度 | FIFO 门票闸门 + 有界并发（默认 4）+ 多实例（同算法 ≤2） | 每任务异步 workLoop + 回调，赶不上就跳过该算法 | 语义一致 |
| 后处理 | YOLOv5/v11/Damo 自研 + 逐类 NMS + ROI + 跟踪 | 生产插件（同名算法） | 参数对齐见 §3 |
| 单通道预览 | 设备侧缩放 + 设备侧画框 + **设备侧 JPEG**（NV12→`bmcv_image_jpeg_enc`，CPU 仅回退） | `JpegEncoderInstance` 设备侧编码 | **已对齐**（`hw_jpeg_ok>0/fail=0`；质量 `AIDETECT_JPEG_QUALITY`） |
| 合流墙 | 4 组 × 3×3，设备侧画布 + `image_copy_to` + 设备侧 JPEG | `MergeInstance`（硬件合流） | 形态一致 |
| 告警图片 | 设备侧画框 + **设备侧 JPEG**（1280×720 / 原尺寸） | 设备侧编码 | **已对齐** |
| 告警视频 | `TsSegmentRecorder`：TS 2s×12 分段环 → ffmpeg remux MP4，HEVC 源转 H.264 | `dump4`：每通道常驻，取 pre/post 进程内写 MP4 | 目标一致（10s、20MB 上限），实现不同 |
| 上报 | HTTP JSON + JWT，告警图/视频路径回填 | 同（`report_address`） | 一致 |
| 配置同步 | 每 2s 从后端 reconcile（任务/ROI/算法参数热更新） | 生产由 Web 下发到 `TaskInstance` | 一致 |
| 子码流切换 | 显式 `AIDETECT_AUTO_SUBSTREAM=1` 才启用，默认按 URL `streamType` | 生产按通道配置 `streamType` | **已对齐**（默认配置驱动） |

| 解码帧率 | 跟源（实测单路 1440p 27.5 fps 解码能力） | 跟源 | — |
| 检测节奏 `frameInterval` | 按任务配置抽帧（默认 5 帧≈3fps） | 同名字段 | 一致 |
| 告警阈值 `detectThreshold` | 每算法可配（如 0.8/0.9/0.4） | `people_*_threshold` 等 | 一致 |
| ROI | 多边形 + 区域线，越界过滤 | 同 | 一致 |
| 告警视频时长 | `pre=round(video_duration×0.5)`、`post=duration-pre` → 实测 **8.98s** | `VideoRecordSec=10` + `VideoRecordPrefix=0.5`（生产 DB `table_preference`，值 10 / 0.500000）→ **前 5s+后 5s** | **已对齐**（比例驱动，不再硬编码 5s） |
| 告警视频编码 | H.264 / 1280×720（HEVC 源转码 `h264_bm`；转码忙时保留 HEVC） | H.264（`Mp4RecorderEngine` 可切 0/1） | **已对齐**（实测 H.264/1280×720） |

| 告警冷却 | `cooldown_time`（默认 180s）+ 算法级 repeat + 每目标 `TargetState`（蓝→红） | 生产 `AlarmIntervalFilter::isAlarmFiltered` + `AlarmRecorder::isSameRectAlarm/getLastALarmTime` + `table_alarm_interval(id,time_ms)`（生产 DB 实表） | **语义一致**：生产按 alarm key 的时间间隔 + 同框判断；我方按目标状态跟踪 + 算法 repeat/任务 cooldown |
| 告警同框去重 | 同一目标 IoU/中心距匹配后只保留一个 `TargetState`，多算法同目标合成一个框 | `isSameRectAlarm`（同算法同框抑制） | 实现不同，结果一致（我方按目标跟踪，避免“同框不同算法规避冷却”） |
| JPEG 质量 | `AIDETECT_JPEG_QUALITY`（默认 90，30~100 clamp） | 生产 `QualityOfPreview`（低/中/高 ≈40/70/90） | 可配；默认值仍偏高 |
| 预览分辨率 | **按源尺寸**（6488 实测 2560×1440；`AIDETECT_PREVIEW_WIDTH/HEIGHT` 可设上限，只缩不放） | 原尺寸（`JpegEncoderInstance` 不缩放） | **已对齐**（ADR-097，取代 ADR-088） |
| 预览帧率上限 | **5 fps**（`AIDETECT_PREVIEW_INTERVAL_MS=200`；实测 4K 3.81 fps、704×576 5.04 fps） | 生产约 3~5 fps* | **已对齐**（ADR-097，取代 ADR-023） |
| 重连退避 | 指数退避 + ISC 候选轮换 + 200ms 开流节流 | 生产有重连机制 | 一致 |
| 解码器生命周期 | 失败 5 次后重建（已修：先释放后创建、失败路径释放、帧缓冲减半） | 常驻不重建 | **生产更优**（重建代价已压到可控） |

## 6. 结论与差距

1. **逻辑栈已对齐**：取流/解码/推理/预览/合流/告警/上报的形态与生产一致；解码从软件换到 VPU 后，
   CPU 从 266~294% 降到 191~197%，dmabuf 从 500~660 降到 290 且恒定。
2. **单路 CPU 仍高于生产**（5.3% vs 3.3%）：主要差在
   ①预览/告警 JPEG 仍走 `bm_image_to_mat`+`cv::imencode`（CPU 编码，生产是设备侧）；
   ②每帧全尺寸 BGR_PLANAR 转换（生产按需缩放）。
   优化这两项预计可再降 1~2 个核。
3. **稳定性仍是短板**：生产连续 5 天 16 小时、1021 线程、dmabuf 0；我们本轮在修
   解码器生命周期崩溃（已改 `shared_ptr` + 读取前快照），需连续 24h 观察。
4. **线程模型**：生产 1021 线程（每通道多线程），我们 268~278，扩展性好但重连风暴时压力集中在少数线程。
5. **缺失的可观测项**：TPU/VPU 利用率（我方 `/get_occupancy` 返回 0）、端到端时延、告警召回/误报率。

## 7. 建议继续采集的参数（用户问「还有哪些参数」）

**性能**：解码帧率/丢帧率、每路 bitrate、CPU 每核分布与软中断、内存带宽、磁盘 IOPS/写入量（分段录制）、
设备内存（BM heap）占用与碎片率、VPP/JPU/VPU/TPU 利用率（连续采样）、温度与降频事件。

**时延**：相机→解码首帧、相机→检测完成、相机→告警上报、预览首帧时间、合流帧间隔抖动。

**业务**：告警召回率/误报率（按算法）、告警重复率、ROI 越界过滤命中率、跟踪 ID 切换率、
模型实例数与调度等待时间、帧间隔达成率（frameInterval 实际 vs 配置）。

**稳定性**：进程重启次数/僵尸次数、长跑 RSS 斜率（trim 前后）、dmabuf 斜率、重连次数/退避时长、
ISC 会话成功率、告警视频生成成功率/耗时、WS 并发客户端数、任务启动耗时。

**前端体验**：预览带宽（KB/s per client）、合流墙端到端帧率、图片清晰度（JPEG 质量）、
标签/框绘制正确率、黑白相机识别（区分源为黑白 vs 转换丢色）。
