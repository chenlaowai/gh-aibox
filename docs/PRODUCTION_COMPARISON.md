# 本机（gh-aibox-dev）与生产盒子对比

> 目的：回答“取流逻辑是否一致、资源占用差在哪、为什么合流卡顿/时间感觉偏慢”。
> 数据来源：本机 `aidetect` 与生产 `app` 的 `/proc` 实测（2026-11-17），生产侧只读；生产 Web 预览用于画面比对。

## 1. 取流与解码链路

| 环节 | 生产（10.10.207.46 / `app`） | 本机（`aidetect`） | 是否一致 |
|---|---|---|---|
| 取流 | 进程内 `StreamFactory` + `media_sdk`（`libavstream.so`，615 个 `media_sdk::*` 符号）解复用，无外部进程 | 进程内 `IngestBridge`（libavformat）拉流+mpegts 封装→本地 UDP；解码器从 UDP 读 | **形态一致**（都是单进程内拉流），实现库不同 |
| 解码 | 每通道 `DecodeInstance`（常驻，不重建），`board::base_frame` 只持句柄 | 每通道 `sail::Decoder`（非 ISC 直连 URL，ISC/文件走 bridge→UDP），**重连会重建解码器** | 不一致（句柄 vs mmap、是否重建） |
| 帧缓冲 | 每通道池化帧，常年 dmabuf 恒 133 | `sail::BMImage` 池化 + mmap（688 条映射），dmabuf 800~930 | 不一致（mmap 数、句柄数） |
| 推理 | `board::base_model`（bmodel） | `sail::Engine`（bmodel） | 等价 |
| 编码/合流 | `JpegEncoderInstance`（设备侧 JPEG）、`MergeInstance` | 瓦片走 `bmcv.imencode`（设备侧），带框预览在 `any_pending` 时走 `cv::imencode`（CPU） | 大部分一致，**带框预览有 CPU 路径** |
| 告警视频 | `dump4`：每通道常驻，从已解包流取 pre/post，进程内写 MP4 | `sail::Decoder::dump()`（进程内，单模式）/ 本地 TS 环 / 外部服务兜底 | 目标一致，**当前待端到端验证** |

## 2. 资源实测（2026-11-18 03:40，修复 pacing 之后）

| 指标 | 生产 `app`（22~36 路，5 天 7 小时） | 本机 `aidetect`（32~36 路） | 判断 |
|---|---|---|---|
| RSS | **2113 MB** | **926 MB** | 我们更省 |
| 线程 | **1021** | **273** | 我们更少 |
| dmabuf fd | **133** | **516** | 我们高约 4 倍（sail 每通道 mmap） |
| dmabuf mmap 条目 | **0** | ~460 | 结构差异 |
| 整机 CPU（`ps %cpu`） | **73%** | **267%** | 单路成本：生产 3.3%/路，我们 8.3%/路（**修复前是 29%/路**） |
| ffmpeg 子进程 | 0 | **0** | 一致 |
| 合流墙帧率 | 生产预览约 3~5 fps | **6.9 fps**（`all_4` 55 帧/8 秒） | 相当或更好 |
| 告警视频 | `dump4` 进程内 | 分段环 → MP4（5.2s / H.264 1280×720 实测可播） | 语义一致 |

**本轮 CPU 从 740% 降到 267% 的关键修复**：`IngestBridge` 对文件源补上了 `ffmpeg -re` 等价的
PTS 节奏控制（之前 14 路 MP4 测试源以磁盘速度解码，白烧 5 个核）。

## 3. 为什么卡顿 / “时间越差越大”

1. **CPU 饱和**：本机 8 核被 680% 打满（生产 75%）。饱和后解码/预览线程抢不到 CPU，合流瓦片更新变慢，
   单通道预览也会掉帧——观感就是“卡、帧率低”。
2. **时间基准不是累积延迟**：对同一相机间隔 91 秒抓两帧读 OSD：
   `11:33:49`（实际 11:33:07）→ `11:35:24`（实际 11:34:38），偏移稳定在 **+42~46 秒**，
   两帧之间 OSD 只多走约 4 秒（读书误差内）。说明是**相机自身时钟比盒子快约 45 秒**，
   不是“越拖越慢”。生产页面同一相机同样有偏差（其 25K 画面比墙钟快约 2 分钟）。
3. **合流 3/4 通道闪烁“正在重连”**：通道 3/4 对应 group 2/3，是 18 路 MP4 测试源。
   这些任务此前用 `sail::Decoder` 直连文件，读完即 EOF → 每 5~10 秒重建解码器，
   日志里出现过 **1280 次重连/10 分钟**。已改为走 ingest bridge 循环播放，
   重连次数降到 **0 次/5 分钟**；但文件循环仍有 100~300ms 空洞（当前用“重新打开”实现），
   观感上会偶发一帧“正在重连”。

## 4. 结论与下一步

- **取流形态已与生产一致**（单进程内拉流、无 ffmpeg 子进程），差异在解码器实现（sail vs media_sdk）与
  缓冲策略（mmap vs 句柄）。
- **最该修的是 CPU**：把 680% 压到 200% 以内，卡顿和帧率问题会同步缓解。重点：
  1) 带框预览的 `cv::imencode`（CPU）改走设备侧（bmcv 画框 + 预渲染底板 + `bmcv.imencode`）；
  2) bridge 的 mpegts 封装/拷贝开销（可评估直接喂 ES 或减少拷贝）；
  3) 每通道推理节奏（按 fps 抽帧，而不是来一帧算一帧）。
- **dmabuf 数量**属于 sail 实现特性，不必强求与生产一致；但要继续观察是否随时间增长（KI-038）。
- **告警视频**：链路已切到 `sail::Decoder::dump()`，与生产 dump4 的思路一致；需一次真实告警验证文件生成。

## 5. 路线 B 实测（2026-11-18）：解码栈是 CPU 差距的主因

单路 `数智技术中心_第二排`（2560×1440 H.264，源 15fps），同一台盒子相继跑 200 帧：

| 解码 | 帧率 | CPU/帧 | 折算 36 路（1440p） |
|---|---|---|---|
| 软件 `h264`（**现有 sail::Decoder 走的**） | 27.9 fps | 35.59 ms | ≈ **1.28 核/路**，36 路约 6 核 |
| VPU `h264_bm`（路线 B） | 27.5 fps | 3.25 ms | ≈ 0.12 核/路，36 路约 0.7 核 |

- `sail::Decoder` 的实现是 `avcodec_find_decoder(codecpar->codec_id)`（软件解码，
  `yuvj420p` 在系统内存）+ `bm_image_copy_host_to_device` + `bmcv_image_vpp_convert`，
  与生产 `media_sdk` 的「VPU 直接出设备帧」不是一回事——这解释了「解码烧 6 核」。
- 路线 B 用 `h264_bm`/`hevc_bm`：帧在设备内存（`data[4]/[5]` 为设备地址），
  直接 `bm_image_attach` 给 bmcv，**没有每帧 mmap、没有主机↔设备拷贝**，
  这也是 dmabuf 数量能向生产（133）靠拢的关键。
- 全链路 PoC（硬解＋bmcv 预处理＋bmrt＋画框＋JPEG）单路 13.24 ms CPU/帧、
  推理 0.13 ms/帧；集成后目标是把单路 CPU 从 7.4% 压到 2% 量级。

详见 `tools/routeb_poc/README.md` 与 `docs/PROGRESS.md` 迭代 98。
## 6. 路线 B 落地后的资源对比（2026-11-18，36 路，盒子 10.10.206.25）

| 指标 | 旧（sail，软件解码） | 新（route B，VPU 硬解） |
|---|---|---|
| CPU | 266~294% | **186~195%** |
| dmabuf fd | 500~660（缓升） | **290（22 分钟恒定）** |
| RSS | 926 MB | 638~919 MB（trim 周期，稳态 ~700） |
| 线程 | 268~339 | 271~273 |
| 解码 | 软件 `h264`（35.59 ms/帧） | `h264_bm`/`hevc_bm`（3.25 ms/帧） |
| 推理 | `sail::Engine`（sail 封装） | `bmrt_launch_tensor_ex` 直调 |
| 库依赖 | libsail.so | **无**（只 bmcv/bmrt/bmlib/ffmpeg） |

- 告警链路抽检：20 分钟 57 张 JPG、53 个 MP4；`ffprobe` = H.264 / 1280×720 / 7.02s。
- 合流墙 `all_3` 1920×1080 九宫格、单通道预览均经 WS 抓帧确认实时画面。
- 已知代价：集成中修掉 4 个 bmcv 语义 bug（stride 数组、缺 alloc、d2s 越界、
  packed→planar），并修掉 `decoder_` 悬垂指针导致的偶发崩溃（改 shared_ptr）。
